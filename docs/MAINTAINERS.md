# Maintainers

How the foundation itself is built, versioned, and kept honest. Consumers don't need this page — start from the [README](../README.md) and the quickstarts.

## Layout

```
crew/
├── roles/<role>/                   # SINGLE SOURCE for the 7 role agents — exactly role.yml + body.md
├── roles/_shared/<part>.md         # text every role carries verbatim, pulled in by `<!-- include: <part> -->`
│   └── expected-local-skills.txt   # backtick-token allowlist: local-skill SLOT names agent bodies may cite
├── skills/<name>/SKILL.md          # one tree → all three harnesses read it (schema-v2 frontmatter)
├── agents/*.md                     # RENDERED Claude subagent files (do not edit)
├── pi-agents/*.md                  # RENDERED pi-subagents files (do not edit) — same names as agents/, registered as crew.<role>
├── pi-extension/index.ts           # EXPERIMENTAL crew_agent tool for pi (opt-in: CREW_PI_AGENT=1); reads pi-agents/*.md
├── docs/CATALOG.md                 # GENERATED skill inventory
├── docs/capabilities.txt           # capability vocabulary (documented in docs/CAPABILITIES.md)
├── templates/AGENTS.md             # the onboarding scaffold (behavioral spine + ▸ Fill blocks)
├── templates/local-skills/         # 5 declared slot stubs
├── scripts/render_roles.py         # role renderer; --check is the CI drift gate
├── scripts/role_contract.py        # shared role posture/runtime-knob contract
├── scripts/frontmatter.py          # dependency-free leading-frontmatter field parser
├── scripts/crew_doctor.py          # deterministic read-only Doctor evidence helpers
├── scripts/crew_inventory.py       # read-only inventory engine (crew-inventory/1) behind the capability map
├── scripts/onboarding_contract.py  # audit/apply lifecycle contract
├── scripts/learn_contract.py       # proposal-queue gates + Doctor evidence; docs/LEARNING.md is normative
├── scripts/gen_catalog.py          # docs/CATALOG.md generator; --check in CI
├── scripts/check_skills.py         # schema-v2 + 110–300 character description gate; --pack, --report-cost, --local
├── scripts/check_skill_layout.py   # skill and consumer-role layout/frontmatter gate
├── scripts/check_links.py          # relative Markdown links resolve inside the repo
├── scripts/check_versions.py       # every manifest version agrees
├── .github/workflows/pack-checks.yml  # reusable workflow: Crew's published checks, run against a pack
├── tests/                          # fixture-driven cross-harness contract regressions
├── package.json                    # pi package manifest
└── .claude-plugin/
    ├── plugin.json                 # Claude plugin manifest
    └── marketplace.json            # this repo doubles as its own marketplace
```

## Editing rules

- **Roles:** a role is exactly two files — a harness-neutral `role.yml` (`name`, `description`, `writes`, optional `dispatch`) and one shared `body.md`. Anything else in a role directory is a build error. `roles/_shared/` is not a role (the renderer skips any `_`-prefixed directory); it holds text every role carries verbatim, which a `body.md` pulls in with an `<!-- include: <part> -->` line of its own. An include that names no `roles/_shared/<part>.md` is a build error. Run `scripts/render_roles.py`, commit source + rendered output together; CI fails on drift. `agents/` and `pi-agents/` are byte-identical below the frontmatter. `role_contract.py` defines posture once and `render_roles.py` translates it into each harness's dialect. Both dialects subtract from the default tool set: Claude uses `disallowedTools`, and pi uses `excludeTools`, which needs the `pi-subagents` `>=0.62.0` floor; the peer pins the tested range `>=0.62.0 <0.82.0`, and widening the top needs a re-check that the newest release still discovers every rendered role with its `excludeTools`. Never render a pi `tools:` key: it is a strict allowlist that also shuts out ambient extensions (MCP). Every pi agent carries `package: crew` (`PI_PACKAGE_NAME`), so it registers as `crew.<role>` and cannot replace pi-subagents' built-in `reviewer`/`researcher`. Claude `drafts` deliberately retains `Write`, so it can create and overwrite files while surgical edit tools are denied. Every role retains shell access, making the posture advisory unless the host sandbox enforces it. The `## Reporting contract` lives once, in `roles/_shared/reporting-contract.md`, and every `body.md` includes it; edit it there, and check its operator-facing counterpart in `templates/AGENTS.md`, which words it differently on purpose but must keep every rule (a test checks).
- **pi extension (experimental):** `pi-extension/index.ts` is runtime TypeScript that pi loads with no build step, and it has no npm dependencies. pi supplies `@earendil-works/pi-coding-agent` and `typebox`, which are imported only after the `CREW_PI_AGENT=1` check, so the extension cannot break a session that has not opted in. It depends on pi's `registerTool`, its CLI flags (`--mode json -p --no-session --append-system-prompt --exclude-tools --model --thinking`) and the JSON-mode `message_end` event: keep it to that surface. Run `tests/test_pi_extension.py` with `PI_CLI` set to pi's `dist/bundle/cli.js`; without it the tests skip. The `pi-extension` CI job pins the tested pi version. Raise that pin and `MIN_PI` together, only after the tests pass on the new version.
- **Per-harness prose is a smell; per-deployment prose is a bug.** Roles used to carry `claude-context.md` / `pi-context.md` appendices. What they actually encoded was not a harness difference but a *runtime* one — an interactive working tree versus a workflow-managed pod — and the pi copy had accumulated one consumer's Argo paths, branch naming and exit contract. The portable default is now the interactive case, in the shared body; a deployment whose runtime differs shadows the rendered agent in **its own overlay**. If you find yourself wanting a per-harness paragraph, check first whether the real axis is the deployment.
- **No runtime knobs in a role.** A role declares who it is and what it may touch — never which model, how hard to think, or how many turns it gets. All three harnesses support those (Claude Code: `model` / `effort` / `maxTurns`; pi: `model` / `thinking` / `turnBudget`; Codex: `model` / `model_reasoning_effort`) and all three inherit sensible values from the dispatching session when they are omitted. Shipping them from a foundation imposes one operator's cost tier and one vendor's model naming on every consumer, and goes stale on every model release. On Codex it is worse than stale: a role file's `model` is applied *after* the spawn arguments, so it silently overrides the orchestrator's explicit choice. `render_roles.py` rejects `model`, `thinking`, `effort`, `model_reasoning_effort`, `turnBudget` and `maxTurns` in `role.yml` by name — a consumer that wants to pin one sets it in its own overlay or harness config, where it belongs.
- **Skills:** schema-v2 frontmatter (`name`, `description` 110–300 chars with discriminating trigger language first, `tier`, `requires`, optional `expects-local`). The maximum is a repository policy chosen to retain useful triggers under observed catalogue pressure, not a frozen product byte limit. No project-specific values — the dividing test is **"no project context baked in"**, not width: a single-language convention skill is fine if any project benefits; anything binding to one deployment's vault, gateway, cluster, secret paths, or domains belongs in that consumer's overlay (deferral goes through an `expects-local` slot).
- **Packs:** sibling `<domain>-skills` plugins meet the contract in [Packs](PACKS.md). Crew never names a pack. The one exception is `MOVED_SKILLS` in `scripts/crew_doctor.py`: migration metadata recording where a removed skill went, so Doctor and Onboarding can point consumers there; no role or skill depends on it. Capability names come from one shared vocabulary, [Capabilities](CAPABILITIES.md) (`docs/capabilities.txt`); `check_skills.py` warns on an unlisted `mcp:` name in both modes, and a new name lands in the doc and the list in one PR. `provides:` is a pack-only field, and Crew's own skills fill no slots. Changing `roles/expected-local-skills.txt` changes what every pack may `provides:`, and `check_skills.py --pack` resolves that list from the Crew install that runs it. A pack may also declare slots of its own in a root `slots.txt` (same format, one stub each under `templates/local-skills/`); they widen only that pack's check, and Crew's run never reads one. A pack ships stubs, not setup skills: Onboarding drives every stub through `pack_slot_proposals`, and `check_skills.py` checks the `crew:discoverable` / `crew:optional` section-marker grammar of every stub in both modes. Adding a name to `roles/expected-local-skills.txt` or `LOCAL_SLOT_VOCABULARY` reserves it, so a pack already declaring that name starts failing its check and shows `DEGRADED` in Doctor — check the known packs before adding a slot. Packs run Crew's checks through [`.github/workflows/pack-checks.yml`](../.github/workflows/pack-checks.yml), a `workflow_call` workflow, so it is public interface: renaming, removing, or re-arguing a script it runs breaks every pack's CI. Change the workflow and `tests/test_pack_workflow.py` together, and treat a breaking change to either as a minor bump at least.
- **Depth modes for artifact-producing skills.** A skill whose output is an artifact — a plan, a spec, a design, a document — offers the same three levels: **Quick** (a fast first pass that asks only what's needed), **Thorough** (a complete pass) and **Critique** (assess something that already exists). The agent picks one from the maturity of the input and the operator can override it; a rich input skips the shaping questions. One consistent control over cost beats re-negotiating it per skill. This is an authoring pattern for those skills, not a rule for every skill — a convention or reference skill has no depth to choose.
- **Generated artifacts:** after any frontmatter change, run `scripts/gen_catalog.py` and commit `docs/CATALOG.md`.
- **Discovery is the harness's job, not ours — and that is a dependency, so it gets verified and dated.** Each supported harness lists installed skills, with their descriptions, to the model itself. Verified 2026-08-15:

  | Harness | Mechanism | Evidence |
  |---|---|---|
  | pi.dev 0.84.1 | `formatSkillsForPrompt` → `<available_skills>` with name/description/location | `core/skills.js:257-278` |
  | Claude Code | system-reminder listing of available skills with descriptions | observed in-session |
  | codex-cli 0.147.0 | model-visible skills list + `skills.list`/`skills.read` tools | binary strings |

  This is why the catalogue needs no in-repo index: one would be a second, staler copy of what the runtime already injects. **Re-verify on a major harness upgrade** — if a harness ever stopped listing skills, roles would still say "you have a list of available skills" and agents would quietly stop loading them.

  **The listing is not guaranteed complete, and roles must not claim it is.** Codex can truncate descriptions or omit skills, and Claude Code can elide descriptions under catalogue pressure. A skill can also be absent because it is in the wrong layout for that harness, has unparseable frontmatter, or sits behind a dangling symlink. So roles state the observable fact (*you have a list*) rather than the mechanism, and instruct agents to report an expected-but-missing skill as drift; `doctor`'s discovery check exists to answer why. Measurements belong in dated evidence, not permanent limit claims.

  Consequently `description` quality is a hard gate here and the catalogue stays small — those are the only two levers on discovery that actually exist.

- **What the inventory can see is a harness dependency too, so it is dated.** `scripts/crew_inventory.py` reads config and skill files and nothing else. It starts a process only for `--probe-versions` (`<cli> --version`). It never runs `claude mcp list`, because that command connects to every configured server. It never runs `codex mcp list` either. MCP records keep name, transport, scope, command basename and source path; env, headers, args and URLs never enter the output, and a test feeds it secret-laden fixtures to prove that. Config shapes below were checked on 2026-10-21 by reading key names only on a maintainer machine:

  | Harness | Read by the engine | Not observable (and why) |
  |---|---|---|
  | Claude Code | `~/.claude/plugins/installed_plugins.json` (`version: 2`, `plugins[id][]` with `scope`, `installPath`, `version`, `projectPath`) joined with `enabledPlugins` from local > project > user settings; skill roots `.claude/skills`, `~/.claude/skills` and each enabled plugin's `skills/`; MCP config from `.mcp.json`, `~/.claude.json` `mcpServers` (user) and `projects[<abs>].mcpServers` (local), honouring that entry's `disabledMcpServers` and `disabledMcpjsonServers`; each enabled plugin's `.mcp.json` or inline `plugin.json` `mcpServers` | MCP tool lists exist only in session. Account-granted connectors are in no config file. A plugin `.mcp.json` was not present on the checked machine, so that shape comes from the plugin docs. |
  | Codex | `~/.codex/config.toml` `[mcp_servers.*]`, plus a project `.codex/config.toml` only when `projects."<abs>".trust_level = "trusted"`; `plugins."<name>@<marketplace>".enabled` resolved to `~/.codex/plugins/cache/<marketplace>/<name>/<version>/`, whose `.codex-plugin/plugin.json` `mcpServers` points at a `.mcp.json`; skill roots `.agents/skills`, `~/.agents/skills`, `~/.codex/skills` and each enabled plugin's `skills/` | MCP tool lists exist only in session. **Unverified:** whether `codex mcp list` only reads config or also connects to servers. Until someone verifies it, the engine does not run it. |
  | pi.dev | `.pi/settings.json` and `~/.pi/agent/settings.json` `packages` (`npm:` under `npm/node_modules/`, `git:` under `git/<host>/<path>`), URL userinfo stripped; skill roots `.pi/skills`, `.agents/skills`, `~/.pi/agent/skills`, `~/.agents/skills` and each package's `skills/` | MCP is reported as `not_observable`: pi reaches MCP through extensions, and the engine reads no config surface for them. |
  | CLIs | `shutil.which` over a bounded set: `cli:*` from installed `requires:`, `--cli` arguments, and the first command token of `.github/workflows/*` `run:` lines (heredoc bodies, continuations, `x=$(…)`, bash builtins, functions the same block defines and PowerShell `Verb-Noun` cmdlets skipped; a step whose `shell:` is not bash or sh is not read). A CLI only a workflow declares is a low-confidence gap: its steps run on CI runners, not this machine | Versions, unless `--probe-versions` runs them. Whether a CLI is authenticated. |

  An agent supplies what only a session can see with `--observations FILE|-`, using Doctor's capture shape (`schema_version: 1`, `harness`, `captured_at`, `source_command`, plus `mcp_servers[{name, tools}]` and `capabilities[{name, state}]`). An observation can raise a provider to `present`, never to `working`. `external:*` capabilities are matched to MCP servers and plugins by name, and to a known CLI on PATH (`gh` for `external:github`), so both a match and a miss are inferences. **Re-verify these shapes on a major harness upgrade.**

## Versioning

One semver line drives all consumers. Claude Code re-fetches only when `plugin.json`'s `version` changes, so **every PR that touches `skills/`, `agents/`, `pi-agents/`, `pi-extension/`, `roles/`, or `templates/` bumps the version in the PR itself** (usually the patch; set minor/major explicitly when warranted) — enforced by the `version-bump` check in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml). On merge, [`.github/workflows/release.yml`](../.github/workflows/release.yml) tags the merged version — tag-only; it pushes nothing to `main`. Keep `plugin.json` == `package.json` == git tag `vX.Y.Z` — `scripts/check_versions.py` enforces the manifests in CI and again before tagging (`--tag vX.Y.Z` also compares a tag). **Claude Code** tracks `main` (always latest); **pi.dev** and **Codex** pin the tag (reproducible) — bump the pin to update.

## CI gates

`validate` (manifests, schema-v2, description budget, layout self-test, consumer-role fixtures, Doctor/Onboarding and pack-workflow unit tests, relative Markdown links resolve inside the repo via `check_links.py`, and every manifest version agrees via `check_versions.py`), `roles-rendered` (render drift + skill-ref resolution), `generated-current` (catalog freshness + templates parse), `pi-extension` (the `crew_agent` contract on a pinned pi, with a fake model and a fake MCP server), `version-bump` (on content change), plus the security floor (gitleaks, osv-scanner, dependency-review). This repo is a **supply-chain root** — its skills and agents load as instructions into every consumer's agents; every change requires owner review.

Workflows reference actions by **major tag** (`actions/checkout@v7`), never a commit SHA or an exact patch version, so fixes arrive without a PR. An owner can move a major tag, so every job keeps the narrowest `permissions:` it needs. An action that publishes no major tag is pinned to its latest release and noted inline; logic small enough to write inline is written inline rather than pulled in as an action. `tests/test_pack_workflow.py` enforces the form for the reusable pack workflow.
